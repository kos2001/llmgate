# 운영 가이드: 보안 · 데이터 · 성능

개발 모드(`llmgate dev`)가 아니라 실제로 띄울 때를 위한 설명입니다. 설정은 모두 `LLMGATE_*` 환경 변수([.env.example](../.env.example)).

## 보안

| 항목 | 동작 | 설정 |
|---|---|---|
| **보안 헤더** | 모든 응답에 `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`. 대시보드(`/dashboard`)에는 엄격한 **CSP**(자기 출처 스크립트만, 인라인 스크립트·외부 호스트 금지, `object-src 'none'`)와 `X-Frame-Options: DENY`(클릭재킹 방지). 관리/인증 JSON(키·사용량·사용자)은 `Cache-Control: no-store` | 항상 켜짐. `/docs` 는 UI 를 CDN 에서 받아 CSP 를 적용하지 않음 |
| **인증 실패 제한** | 같은 주소에서 **거부된 자격 증명**(틀린 API 키·관리자 토큰·JWT)이 한도를 넘으면 잠시 `429`(`Retry-After`). 자격 증명이 없는 요청이나 권한 부족(403)은 세지 않음. 성공해도 기록을 지우지 않음(낮은 권한 계정으로 카운터를 초기화하는 우회 방지) | `AUTH_FAIL_LIMIT`(기본 30), `AUTH_FAIL_WINDOW_S`(60), `0`=끔. 프로세스 메모리 기준이고 리버스 프록시 뒤에서는 모든 클라이언트가 프록시 주소로 보이므로 한도를 올리거나 프록시에서 처리 |
| **업스트림 키 암호화** | 프로바이더 API 키를 `enc:v1:<Fernet>` 으로 저장해 DB 파일·백업이 유출돼도 상위 서비스 키가 노출되지 않음. 게이트웨이 API 키는 원래 해시만 저장 | `llmgate genkey` 로 키 생성 → `ENCRYPTION_KEY`. 기존 평문은 `llmgate encrypt-secrets` 로 변환. **로테이션**: 새 키를 앞에 두고 쉼표로 이어(`NEW,OLD`) `encrypt-secrets` 실행 후 OLD 제거. 키가 없거나 틀리면 요청이 명확한 500 으로 실패(암호문은 노출되지 않음) |

그 밖에: 관리자 토큰은 상수 시간 비교, 세션은 `HttpOnly; SameSite=Lax` + 쓰기 요청 CSRF 헤더, 알고리즘 고정 JWT 검증 ([auth.md](auth.md)).

> 이 게이트웨이는 **TLS 를 직접 처리하지 않습니다.** HTTPS 는 앞단 프록시(nginx, Caddy, 로드밸런서)에서 종료하고 `LLMGATE_COOKIE_SECURE=true` 로 두세요.

## 데이터 수명 주기

사용 기록(`usage_logs`)은 요청마다 한 줄씩 쌓입니다.

- **내보내기**: 대시보드 > 사용 로그의 *CSV 내보내기 / JSONL*(현재 기간·필터 기준), 제어 탭의 *전체 CSV 내보내기*, 또는 `GET /admin/api/usage/export?format=csv|jsonl&days=30&model=…&only_errors=true`. 페이지 단위로 스트리밍해 수백만 행도 메모리를 거의 쓰지 않습니다. UTF-8 BOM 이 붙어 Excel 에서 한글이 깨지지 않으며, `=`·`+`·`-`·`@` 로 시작하는 텍스트(앱 이름, 사용자, 오류)는 앞에 `'` 를 붙여 **스프레드시트 수식으로 실행되지 않게** 합니다.
- **보존 기간**: `USAGE_RETENTION_DAYS` / `AUDIT_RETENTION_DAYS`(0=영구 보존). 백그라운드에서 6시간마다 오래된 행을 5,000행씩 지웁니다. 감사 로그는 "누가 무엇을 바꿨나"의 기록이라 별도로 설정해야 지워집니다. 즉시 지우려면 제어 탭의 *오래된 로그 삭제*(admin) 또는 `POST /admin/api/storage/prune?days=90`(1일 미만은 거부).
- **백업**: `llmgate backup out.db` — SQLite 온라인 백업 API 로 **게이트웨이가 쓰는 중에도 일관된 복사본**을 만듭니다(기존 파일은 덮어쓰지 않음, 권한 600 시도). 백업에도 키 해시와 프로바이더 자격 증명이 들어 있으니 비공개로 보관하세요(암호화를 켰다면 암호문).
- **상태**: 대시보드 제어 탭의 *저장소* 카드 또는 `GET /admin/api/storage`(DB 크기, 행 수, 가장 오래된 기록, 보존 설정).

## 성능 (측정, 그리고 한계)

`python tools/bench.py --requests 1500 --concurrency 20` 은 **mock 엔진 · 게이트웨이 · 부하 생성기를 별도 프로세스**로 띄워 게이트웨이가 더하는 비용만 잽니다(엔진 토큰 지연 0).

Windows 노트북(파이썬 3.12, 루프백)에서 측정한 결과 — *참고용이며 용량 보장이 아닙니다*:

| 구성 | req/s | p50 | p95 |
|---|---|---|---|
| mock 엔진 직접 (c=20) | ~700 | 21 ms | 71 ms |
| 게이트웨이 경유, 비스트리밍 (c=20) | ~330 | 42 ms | 150 ms |
| 게이트웨이 경유, 스트리밍 (c=20) | ~280 | 59 ms | 161 ms |

- 게이트웨이가 더하는 지연은 대략 **+20 ms (p50)**. 프로파일링 결과 요청당 CPU 는 약 2~3 ms 이고 **지배적인 병목은 없습니다**(요청당 SQL 약 10개로 전체의 8% 정도, 나머지는 HTTP 클라이언트·파이썬 일반 비용). 그래서 단일 워커는 약 300 req/s 부근에서 포화됩니다.
- **워커를 늘려도(`uvicorn … --workers N`) 이 측정에서는 처리량이 늘지 않았는데**, 이는 게이트웨이가 아니라 mock 엔진(단일 파이썬 프로세스, 직접 호출이 ~460 req/s 에서 포화)과 부하 생성기가 먼저 한계에 닿기 때문입니다. 따라서 **워커 확장 효과는 이 장비로 입증하지 못했습니다.** 실제 엔진 앞에서 직접 측정하세요.
- 워커/인스턴스를 늘리면 **RPM·동시 요청·쿨다운·응답 캐시 상태는 프로세스별**입니다(한도가 프로세스 수만큼 느슨해짐). 공유 저장소(Redis 등)는 아직 없습니다.
- LLM 응답 시간(수백 ms ~ 수십 초)에 비하면 +20 ms 는 작지만, 임베딩처럼 아주 짧은 호출을 초당 수천 건 처리해야 한다면 별도 검증이 필요합니다.
